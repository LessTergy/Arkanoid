# AGENTS.md

Инструкции для AI-агентов, работающих с проектом `Arcanoid`.

## Язык и коммуникация

- Основной язык общения с пользователем: русский.
- Объяснения, отчеты о работе и вопросы пользователю пиши на русском.
- Имена классов, методов, полей, файлов, namespace и публичных API оставляй на английском.
- Комментарии в коде добавляй только при реальной необходимости. Если комментарий нужен, пиши его на английском.
- Не добавляй комментарии, которые пересказывают очевидное поведение кода.

## Область проекта

- Основной код проекта находится в `Assets/Content/Scripts`.
- Сторонний код в `Assets/3rd-Party` не изменяй без явной необходимости.
- Unity-generated и временные директории (`Library`, `Temp`, `obj`, `Builds`, `Logs`) не редактируй вручную.

## Обязательное использование MCP CodeGraph

- Перед началом любой теоретической или практической работы обязательно сначала обращайся к MCP CodeGraph.
- Используй CodeGraph для точного определения затрагиваемых файлов, скриптов, классов, методов и функций, а также всех их входящих и исходящих зависимостей.
- До формирования выводов, рекомендаций, плана реализации или внесения изменений изучи через CodeGraph соответствующие символы, связи, цепочки вызовов и область влияния.
- Для каждого нового вопроса или новой задачи выполняй отдельный релевантный запрос к CodeGraph, даже если ранее в рамках сессии граф уже использовался.
- Запрещено делать теоретические выводы, давать технические рекомендации, предлагать изменения или вносить любые правки в проект без предварительного анализа через CodeGraph.
- Если CodeGraph недоступен, проект не проиндексирован или полученных данных недостаточно для понимания целостной картины, не продолжай работу. Сообщи пользователю о блокирующей причине и запроси восстановление доступа или индексации.
- Не подменяй анализ зависимостей через CodeGraph поиском по тексту, ручным чтением отдельных файлов или предположениями. Дополнительные инструменты можно использовать только после CodeGraph для уточнения деталей, которые отсутствуют в его данных.

## Обязательное уточнение требований

- После анализа через CodeGraph и полного изучения доступного контекста явно проверь, остались ли белые пятна, неоднозначности или недостающие требования, критичные для корректной реализации задачи.
- Критичными считай неизвестные данные, от которых зависят архитектура, поведение механики, публичные контракты, формат данных, интеграции, пользовательский сценарий, критерии готовности или выбор между несовместимыми реализациями.
- Если остался хотя бы один критичный вопрос, не составляй окончательный план реализации, не вноси изменения и не начинай практическую часть задачи. Не заполняй пробелы предположениями.
- Собери все выявленные критичные вопросы и запроси у пользователя конкретную уточняющую информацию. По возможности задавай их одним компактным списком, чтобы сократить число итераций.
- После получения ответа повторно проверь целостность требований с учетом CodeGraph и новой информации. Если появились новые критичные вопросы, снова остановись и запроси уточнение.
- Переходить к окончательному плану и реализации разрешено только тогда, когда получены ответы на все критичные вопросы и больше не осталось неопределенности, способной повлиять на корректность результата.
- Некритичные детали, не влияющие на корректность или совместимость решения, можно закрывать явно обозначенными разумными допущениями.

- Результаты Context7 обязательно фиксируй в `Docs/AgentKnowledgeBase.md` до продолжения теоретической или практической работы. Не продолжай работу, опираясь только на временный ответ Context7.

## Общие принципы кода

- Следуй SOLID там, где это действительно улучшает структуру.
- Применяй KISS, DRY и YAGNI.
- Предпочитай простой, чистый и читаемый код, который легко читать как обычный текст.
- Не добавляй абстракции "на будущее".
- Не усложняй решение ради паттерна.
- Не дублируй логику, если ее можно вынести без ухудшения читаемости.
- Предпочитай самодокументируемые имена и маленькие методы избыточным комментариям.

## C# и Unity кодстайл

- Всегда используй фигурные скобки для `if`, `else`, `for`, `foreach`, `while`, `do`, `using`, `lock` и других блочных конструкций.
- Не пиши однострочные управляющие конструкции без блока.
- Нельзя:

```csharp
if (isReady) return;
```

- Нужно:

```csharp
if (isReady)
{
    return;
}
```

- Однострочные методы и свойства тоже оформляй с фигурными скобками, если это обычный метод или блоковая логика.
- Expression-bodied members используй только когда это уже соответствует локальному стилю файла и не ухудшает читаемость.
- Приватные поля предпочитай именовать в стиле `_camelCase`, если файл не использует другой устойчивый локальный стиль.
- Сериализуемые приватные поля оформляй как `[SerializeField] private ...`.
- Публичные поля в `MonoBehaviour` и `ScriptableObject` не добавляй без необходимости; предпочитай `[SerializeField] private` плюс публичное read-only свойство, если нужен доступ извне.
- Сохраняй существующие namespace и структуру папок проекта.
- Избегай runtime-поиска зависимостей через `GetComponent`, `GetComponents`, `GetComponentsInChildren`, `Find`, `FindObjectOfType` и похожие API. Используй их только когда это действительно оправдано архитектурно. В обычном случае объявляй `[SerializeField] private` поле и связывай зависимость через Inspector.
- Не добавляй проверки на `null` по умолчанию для обязательных зависимостей. Если скрипт не может корректно работать без зависимости, пусть ошибка настройки проявится явно, а не будет скрыта тихим `return`. Проверяй `null` только для действительно опциональных ссылок, внешних данных или веток, где отсутствие значения является ожидаемым состоянием.

## Unity Inspector

- Для сериализуемых полей в `MonoBehaviour`, `ScriptableObject` и `[Serializable]` классах/структурах добавляй `[Header]`, если это помогает логически разделить поля на группы в Unity Inspector.
- Названия `Header` должны быть понятными для команды и отражать смысл группы.
- Не добавляй лишние `Header`, если в классе одно-два очевидных поля и группа не улучшает Inspector.

## Работа с Unity

- Не меняй сцены, префабы или настройки проекта без необходимости для текущей задачи.

## Тестирование и проверка

- Минимальная проверка для C# изменений: отсутствие ошибок компиляции.
- Для изменений, влияющих на Inspector, проверь, что атрибуты Unity стоят в корректном порядке и не ломают сериализацию.

## Git и существующие изменения

- Не откатывай изменения пользователя без явной просьбы.
- Перед редактированием учитывай текущее состояние рабочего дерева.
- Если в файле уже есть несвязанные изменения, работай аккуратно поверх них и не переписывай файл целиком без необходимости.
- Не выполняй destructive git-команды (`reset --hard`, `checkout --`, удаление файлов) без явного подтверждения пользователя.
