# Arkanoid

Классический 2D Arkanoid на Unity. Проект создаётся как законченное портфолио-приложение с понятной архитектурой, автоматическими тестами и обоснованным применением VContainer, Addressables, Decorator, Composite и Chain of Responsibility.

Этапы 0–7 завершены, Gate 7 пройден; пользователь подтвердил Stage 7 и Android build 2026-10-10. Stage 8 содержит общий контракт effects, definitions, фабрику и выбор по весам. По решению пользователя 2026-10-11 игровые бонусы самостоятельны: ExpandPaddle (×1.5 ширина), AddLife (+1 жизнь до 5), DoubleScore (×2 следующие начисления). Rescue и Comeback удалены; AddLife использует отдельный зелёный pickup. Текущий профиль пользователя сохранён: одна запись DoubleScore, Weight=1, Chance=1. Импорт после правки, тесты и приёмка Unity/Android ожидаются по [чек-листу Stage 8](<Development Plan/Stages/08-bonus-checklist.md>); Gate 8 открыт. Подробный статус — в [Development Plan](<Development Plan/README.md>).

## Требования

- Unity `6000.3.18f1`;
- Addressables `2.9.1`;
- целевые платформы первой версии — Android и iOS, портретная ориентация.

## Запуск в Unity Editor

1. Добавить корневую папку проекта в Unity Hub.
2. Открыть проект в Unity `6000.3.18f1` и дождаться импорта assets и компиляции scripts.
3. Настроить базовый prefab блока: назначить `Definition`, `Body Renderer`, `Shield Renderer` и world-space TMP `State Label`. Шаги для оболочки, текста и prefab-вариантов — в [P6.9–P6.10](<Development Plan/Stages/06-brick-hit-chain.md>). Все ссылки обязательны. Существующий `Assets/Content/Data/Bricks/BrickDefinition.asset` соответствует Normal; рядом добавлены `Durable`, `Shielded`, `Indestructible`. Для запуска уровня нужен хотя бы один активный разрушаемый блок.
4. Открыть сцену `Assets/Content/Scenes/Bootstrap.unity` и нажать Play.

## Проверка

В Unity Test Runner выбрать PlayMode и запустить `BootstrapSmokeTests`, `LevelCompletionSmokeTests` и `LifeLossSmokeTests`. Они проверяют переход между сценами, сроки жизни scopes, сброс score/combo/double и восстановление блоков при restart, инициализацию Addressables/DOTween, завершение смешанного уровня после последнего начисления и потери жизни. Обычный запуск `Bootstrap` через Play проверяет автоматический старт отдельно: Test Runner создаёт корневой scope до начала тела теста.

В EditMode `ScoreServiceTests` проверяет накопление рассчитанных очков, публикацию обновлённого total, нулевое начисление и сохранение счёта при ошибках. Правила base, combo и double проверяются отдельными тестами калькуляторов и композиции.

Для HUD назначить новый текст TextMeshPro в поле `Combo Text` компонента `GameplayHudView`; шаги находятся в [P5.9](<Development Plan/Stages/05-score-decorator.md#назначение-inspector-пользователем>). При старте видны `Score: 0` и `Combo: 0`, уничтожение увеличивает оба значения, потеря жизни сбрасывает только комбо, Restart начинает счёт заново. `ComboModelTests` также проверяет события изменения комбо.

PlayMode-класс `GameplayScoreIntegrationTests` проверяет физические попадания, начисление по settings, отсутствие очков за щит/повреждение/indestructible и повторное попадание после уничтожения, сохранение повреждений и total при потере жизни, сброс combo и отклонение отрицательного входа в `ScoreService`. Для сценовой регрессии нужны минимум три активных разрушаемых блока, среди них HP > 1 и щит, плюс хотя бы один indestructible; подойдут четыре текущих пресета с назначенными presentation-ссылками.

Запустить также EditMode `BrickHitChainTests` и PlayMode `BrickHitIntegrationTests`. Цепочка `Indestructible → Shield → Damage` снимает один shield либо одно HP; последний shield полностью поглощает удар. Каждый блок хранит своё состояние, повтор после уничтожения не публикует событие повторно. LevelView инициализирует все активные блоки, но учитывает для победы только разрушаемые; очки читаются из проверенных settings. Подпись показывает оставшееся HP/щит, оболочка исчезает при последнем заряде. Indestructible остаётся после завершения уровня.

`BrickHitIntegrationTests` создаёт временный смешанный уровень и проверяет визуальные данные, реальный score handler, валидацию definition до изменения score/combo, нулевой score и ошибку уровня без активных разрушаемых. Тесты, ручной сценарий и player build этапа 6 подтверждены пользователем; критерии находятся в [документе этапа](<Development Plan/Stages/06-brick-hit-chain.md>).

## Почему Chain of Responsibility

Цепочка `Indestructible → Shield → Damage` явно задаёт приоритет защиты: каждый handler применяет своё правило либо передаёт запрос дальше, а поглощение щитом останавливает обработку даже при последнем заряде. Это позволяет отдельно проверять делегирование и остановку через подставной next. Для трёх текущих правил достаточно и одного processor с ранними return; цепочка выбрана как обязательный паттерн проекта ценой дополнительных классов.

Новый handler оправдан самостоятельным согласованным правилом защиты, которое меняет обработку попадания и имеет определённое место в цепочке. Его подключают в `GameplayLifetimeScope`; новые значения HP, score, зарядов щита, цвет или prefab-пресет требуют только настройки definition.

## Общий контракт эффектов и Composite

Pickup вызывает один `IBonusEffect.Apply(context)`; каждый из трёх игровых бонусов выполняет только своё действие. ScriptableObject definition связывает effect и prefab, фабрика проверяет данные до создания pickup. Шанс и веса вариантов принадлежат отдельному drop-профилю; состояние партии хранится в существующих моделях.

Composite первоначально реализован для группирующих бонусов, затем пользователь исключил их из контента. Механизм и технические тесты вложенности, порядка и валидации сохранены в рамках обязательного паттерна проекта. В текущей игре его демонстрации нет; выбор уместного применения для итогового проекта остаётся отдельным вопросом.
